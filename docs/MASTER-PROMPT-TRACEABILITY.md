## Status definitions

- **Implemented in source:** a usable code path exists, but may still need owner configuration or live verification.
- **Partial:** some requirements exist, while other named workflows or modules remain missing.
- **Placeholder / deferred:** explicitly not implemented; the application must not claim it is available.
- **Not verified:** source exists but end-to-end behaviour, deployment, permissions or external integration has not been tested with real accounts.

## Support communication enhancement (25 November 2026)

- The existing Help & Support ticket now includes a private multi-message conversation thread. Customers and authorised staff can continue the discussion without overwriting the original enquiry or a single staff-reply field.
- Conversation records live under `supportTickets/{ticketId}/messages`, are readable only by the ticket owner and authorised staff, and are append-only. Firestore rules reject cross-customer reads, unauthorised writes, edits and deletes.
- The thread is mounted inside the existing portal support card. It does not introduce email, SMS or automated WhatsApp delivery; those external messaging services remain unconfigured.
- A focused Firestore Emulator test covers ticket ownership, staff participation and immutable message history. Owner-operated acceptance test T27 remains not run until separate live customer/staff accounts are tested.

## Recently added workflows

- Account portal render-error boundary: catches React render failures in the account portal and displays a recoverable error message instead of leaving the portal area blank. The original account navigation/blank-page scenario still requires reproduction and testing with the owner’s Firebase account.

- Refund request and manual refund record workflow: customers can submit one refund request per verified payment; Finance/Super Admin can review, approve/reject and record a completed bank-transfer reference. Firestore binds the refund document to its payment and owner. The platform does not initiate transfers or automatically reconcile refunds into POS/statutory accounts.

- Product catalogue enhancement: Super Admin can configure up to eight additional HTTPS image views, colours, fabric options and customisation options; customers can switch product image views and inspect the available design options. Existing product records without the new optional arrays remain eligible for stock adjustments.

- Guided style recommendation wizard: customers choose occasion, category, garment, colour, style direction, budget and optional reference notes, then receive three deterministic starting suggestions and can send the brief to the configured WhatsApp contact. It is not AI, live inventory or a quotation.
- Appointment alternative proposals release the previously reserved confirmed slot in the same Firestore transaction; customer acceptance reserves the proposed slot atomically. Institute session scheduling now atomically reserves five-minute instructor and onsite venue time-block documents in the same Firestore transaction as session creation; completion or cancellation releases those locks. The five-minute granularity is intentionally conservative and can reject bookings that are close together but do not actually overlap.
- Dedicated standalone public page layouts are mounted for About, Collections and categories, Fabric Gallery, Fashion Institute, Courses, Admissions, Contact and FAQ; customer/student/admin deep links still use the role-protected portal rather than independent route components.

- Customer privacy request centre for access, correction and deletion requests. A request is not an automatic data erasure; staff must review retention requirements and connected Drive records.
- Public fabric catalogue with Super Admin create/edit/archive controls.
- Customer loyalty and VIP benefits panel. Points are currently adjusted manually by Super Admin and recorded in an append-only transaction history.
- Customer referral submission and Super Admin review. Referral status does not automatically award points.
- Corporate and bulk-order enquiry form with customer status visibility and Super Admin / Fashion Manager review.
- Private payment evidence link in Finance review; uploaded evidence is not proof that the bank transfer has cleared.
- Payment review JSX syntax fix was committed after a failed build. Bank account selection/copy controls and stricter Firestore tests for account publishing were added; always use the newest Actions run as the source of truth for deployment status.

## Implementation addendum — phases 1–11 incremental work

**Branch:** `feature/complete-master-prompt-phases-1-11`

The following changes are additive and intentionally reuse existing Firestore records and portal workflows:

- **Catalogue-to-order handoff:** Customer product cards now offer a "Request this design" action. It pre-fills the existing custom-order form with the selected product, mapped clothing category and available first fabric/colour options. It does not create an order or promise stock availability, price or delivery.
- **Measurement field reference:** Every currently supported garment profile now has an expandable field-by-field tape-placement reference. It supplements the existing diagrams and guidance; it does not replace designer verification.
- **Appointment review:** The appointment calendar and Operations Centre identify potential exact date/time/designer collisions among non-cancelled bookings. This is a review aid only: it does not calculate appointment duration or mutate reservations.
- **Business Operations & Quality Centre:** A read-only, role-aware view summarises active/overdue production work, appointment review groups, measurement verification backlog and finance declarations awaiting review. Super Admin can export selected operational CSV reports without customer contact details. It does not write to business records or treat payment evidence as proof of cleared funds.
- **Preservation:** No existing Firestore collections, document schemas, authentication flows, security rules, Google Drive integration or payment workflows were changed by this addendum.
